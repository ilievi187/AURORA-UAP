# AURORA V1.4.2 — D1 release and verification

Production is currently a safe staged V1.4.1: the public D1 register is **not** verified as active. Existing GitHub integration does not grant Cloudflare write permission.

## What is implemented

The reviewed SQL seed generator no longer emits manual BEGIN/COMMIT statements, which are incompatible with Cloudflare D1 Wrangler execution. The release verifier checks actual HTTPS endpoints, not fixture data. In staged mode, APIs must return 503 while the existing eight sourced reference cases remain online; in active mode, the verifier checks real D1 counts, country/year facets, source links, case IDs, assessment statuses and last successful sync.

Read-only verification CLI:

    node scripts/check-registry.mjs --base https://aurorauap.org --mode staged

After real D1 activation:

    node scripts/check-registry.mjs --base https://aurorauap.org --mode active

Only the AURORA domain and its Cloudflare Pages preview hosts are accepted. The script never makes write requests.

## Option A: Run from GitHub without cloud secrets

Open [AURORA Registry Release Verification](https://github.com/ilievi187/AURORA-UAP/actions/workflows/verify-registry.yml), choose Run workflow, input the target URL and expected mode (staged or active). This action only fetches public URLs.

## Option B: Create and seed a real D1 safely

The authorized Cloudflare account owner must first create a D1 database named aurora-uap-cases, or verify that one already exists. There is no Cloudflare administration tool with confirmed write access in this conversation.

In GitHub repository Settings > Environments, create an environment named aurora-d1-ops with required reviewer protection if possible. Configure two environment secrets:
- AURORA_CF_D1_TOKEN — narrowly scoped Cloudflare API token with D1 permissions for the correct account
- AURORA_CF_ACCOUNT_ID — the correct Cloudflare account identifier

Never paste credentials into repository files or chat.

Open [AURORA D1 Bootstrap (manual)](https://github.com/ilievi187/AURORA-UAP/actions/workflows/d1-bootstrap.yml). Choose Run workflow on main and enter the UUID of the existing aurora-uap-cases D1 database. Type the exact manual approval phrase SEED_EXISTING_AURORA_D1.

The job uses Wrangler 4, verifies that the UUID and database name match the authenticated account, runs the SQLite-backed tests, applies the reviewed schema, imports only the three original AARO case summaries and performs a remote query to verify the three real rows. It fails closed on missing secrets, a mismatched database or failed checks. It cannot enable the public registry or configure Pages.

## Separate Pages activation

1. In Cloudflare Workers & Pages > aurora-uap > Settings > Bindings, attach the newly verified database as D1 variable DB. Prefer a distinct preview D1 database for test deployments; redeploy to activate the binding.
2. Leave AURORA_REGISTRY_PUBLIC unset while checking the remote records. This preserves the sourced historical archive and keeps the public D1 API unavailable.
3. Only when the D1 has been verified, set the non-secret environment variable AURORA_REGISTRY_PUBLIC to the exact value enabled on the intended Pages environment. Redeploy and run the active release verifier. Roll back by unsetting this variable and redeploying if any check fails.
4. Confirm mobile and desktop visually. R2 upload, private contacts, public submission, outbound email, and Hermes AI writes remain OFF.

Cloudflare D1 and Pages references:
- https://developers.cloudflare.com/d1/wrangler-commands/
- https://developers.cloudflare.com/pages/functions/bindings/
